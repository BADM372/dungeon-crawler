From here to there

A spider sees you. Between you and the spider is a wall. How does the spider know to walk around it?

The spider does not have eyes like you. It cannot look at the room and "just see" the way. It needs a method, a step-by-step recipe. In computer science, such a recipe is called an algorithm.

Finding a way is needed all over the game:

  • Monsters chase you, walk home, and wander around.
  • You click on the floor, and the hero walks there, around obstacles.
  • The world builder plans routes between the gates of every cube.

The floor is a grid

Each cube is 16 by 16 cells. For walking, the game only asks: from this cell, which of my four neighbours (east, west, south, north) can I step to?

A neighbour is blocked by walls, cliffs that are too high, fences, water, and ceilings too low for your body. (A big Stunder needs more headroom than a little spider!)

A map of "who can step where" is called a graph.

Try it: the flood

Press Flood. The search spreads out like water poured on the floor: first every square 1 step away, then 2 steps, then 3... The first time the water reaches the goal, we have found the shortest way. Draw walls and try to trap it!

S is the start, G the goal. The colours show how many steps away each square is. Ignore the A* button for now, it comes next.

Breadth-first search, and breadcrumbs

The flood has a real name: breadth-first search, or BFS. "Breadth first" means it goes wide before it goes far.

How does it know the way back? Every time the water reaches a new square, it leaves a breadcrumb there: "I came from that square". At the goal, follow the breadcrumbs back to the start, and turn the list around. That's the path!

Monsters use BFS to chase you. Your hero uses it too when you click on the floor. If the spot cannot be reached, the hero walks to the reachable square closest to it.

Monsters give up

Searching a whole cube for every monster, many times a second, would be slow. So each search has a limit:

noticing you10 steps
chasing you16 steps
walking home40 steps
wandering about6 steps

If you are further away than the limit, the monster cannot find a way to you. Climb a ladder, and they lose you!

Monster brains

A*: searching with a hunch

The flood is a bit silly: it searches in all directions, even away from the goal. A* (say "A star") is smarter.

For every square it could look at next, it adds up two numbers:

  • how many steps it took to get there, and
  • a guess of how many steps are left: just the distance across and down, as if there were no walls.

It always continues from the square with the smallest total. So it heads towards the goal first, and only spreads out when a wall is in the way.

Go back to the demo and compare: A* usually looks at far fewer squares, and still finds a shortest path.

The world builder uses A*

When the builder plans the routes through a cube, a step is not just "walk": it can be a stair, a bridge, a ladder, a jump or a drop. Each costs a different amount, so the builder prefers walking.

Two more tricks:

  • Moves already used by another route cost almost nothing. So routes share stairs and bridges instead of building new ones.
  • Every square gets a small random extra cost. So two cubes with the same shape still get different routes.

Can it see me? Line of sight

A monster only starts chasing you if it can see you. The Fire-face only spits fireballs if nothing is in the way.

The test is simple: walk along the straight line from the eye to you, in tiny steps of 0.15 cells, and at each step ask "is this inside something solid?". If any step is, the view is blocked.

Simple, and fast enough to do for every monster several times a second.

The real code: a monster's path

export function findPath(a, b, maxLen, height = 0.9) {
  if (!a || !b || !walkable(a, height) || !walkable(b, height)) return null;
  const prev = new Map([[a, null]]);
  let front = [a];
  for (let d = 0; d < maxLen && front.length && !prev.has(b); d++) {
    const next = [];
    for (const f of front) for (const g of neighbors(f, height))
      if (!prev.has(g)) { prev.set(g, f); next.push(g); }
    front = next;
  }
  if (!prev.has(b)) return null;
  const path = [];
  for (let f = b; f; f = prev.get(f)) path.unshift(f);
  return path;
}

a and b are floors (cells you can stand on). height is how tall the monster is.

prev is the breadcrumb map: for each floor, where we came from.

front is the edge of the water. Each round of the loop makes the next ring, next, from all neighbours not seen before.

The loop stops after maxLen rounds (the "give up" limit), when the water cannot spread, or when b is reached.

The last loop follows the breadcrumbs back from b, and unshift puts each one at the front of the list, so the path comes out in the right order.

The real code: A* in the world builder

export function search(ctx, from, goal, jitter, have) {
  const gs = new Float64Array(SZ).fill(Infinity), prev = new Array(SZ).fill(null);
  const hfn = f => Math.abs(f.x - goal.x) + Math.abs(f.z - goal.z);
  const open = new Heap();
  gs[from.id] = 0; open.push(hfn(from), from);
  while (open.size) {
    const cur = open.pop();
    if (cur === goal) break;
    for (const mv of movesFrom(cur)) {
      const ng = gs[cur.id] + (have.has(moveKey(mv)) ? 0.2 : mv.cost + jitter[mv.to.id]);
      if (ng < gs[mv.to.id]) {
        gs[mv.to.id] = ng; prev[mv.to.id] = mv;
        open.push(ng + hfn(mv.to), mv.to);
      }
    }
  }
  /* ... follow prev back from the goal, like BFS ... */
}

gs: the cheapest cost found so far to reach each floor. hfn: the hunch, the distance across plus the distance down.

open is a heap: a to-do list that always hands you the item with the smallest number first. The game's heap is in src/core/heap.js, only 30 lines long. The A* in the demo uses it too.

See the trick from the last slide? A move already in have costs only 0.2. Otherwise it costs its normal cost plus a little random jitter.
